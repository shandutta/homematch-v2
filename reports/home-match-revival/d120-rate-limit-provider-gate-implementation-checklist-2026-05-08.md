## 2. Non-memory config behavior (what must remain true until a row above is approved)

The repo's job until an option is approved is to make every non-`memory` value visibly fail closed. The following statements are the executable contract; any pull request that loosens one of them must update both this section and the corresponding test.

- `RATE_LIMIT_STORAGE_PROVIDER` is non-secret configuration evidence. Absence, empty string, and whitespace-only values are equivalent to `memory`.
- Provider names are normalized via `trim().toLowerCase()`. A normalized value of `memory` is the only path that returns `{ provider: 'memory', durable: false }` from `getConfiguredRateLimitStorageProvider()`.
- Every other normalized value throws `Durable rate limiter storage provider "<name>" requires an approved adapter before production use`. There is no silent fall-back to memory and no silent promotion to durable.
- The throw happens at limiter creation time (`createRateLimiter` calls `getConfiguredRateLimitStorageProvider`), so a misconfigured deploy fails on first request rather than running with a half-configured store.
- Test/CI bypass behavior is unchanged: `shouldBypassRateLimit()` returns true under `NEXT_PUBLIC_TEST_MODE=true` or `NODE_ENV=test`, **unless** `RATE_LIMIT_ENFORCE_IN_TESTS=true` or `RATE_LIMIT_ENFORCE=true` is set. The bypass is independent of `RATE_LIMIT_STORAGE_PROVIDER`; setting the provider to a non-`memory` value in a test environment must still throw at construction unless the bypass short-circuits the limiter call entirely.
- Limiter source must continue to deep-import `rate-limiter-flexible/lib/RateLimiterMemory` and must not import any forbidden SDK module. `package.json` (in any of `dependencies`, `devDependencies`, `optionalDependencies`) must not declare any forbidden SDK package.
- The error message string is part of the contract: it is asserted by the guard test and referenced by the closure-matrix language. It must not be softened (e.g., to a warning, a console log, or a generic `Error`) without rewriting both the test and this report.

## 4. Spending / paid-resource approval boundary

This boundary is the one Phase 0/1 cannot decide on its own. The repo cannot itself authorize paid usage; it can only refuse to execute against a paid resource until the authorization exists.

- Authorizing a provider commits the project to a recurring spend (Upstash, Vercel KV, Cloudflare KV, hosted Redis) or to additional load on existing paid infrastructure (Postgres/Supabase). Approval must come from the budget owner and must name the provider, the expected steady-state cost band, and the runaway-cost cap.
- The repo must not provision the resource. Provisioning (account creation, project creation, KV/namespace binding, network peering) happens outside the repo by ops. The repo only consumes already-provisioned credentials via secrets that exist outside the repo.
- Credentials for the approved provider must be stored in the production secrets manager. They must not appear in `.env`, `.env.example`, `.env.prod`, `config/*.json`, fixtures, tests, this report, or any other tracked file. The existing D4 invariant (`reports/home-match-revival/p0-p1-env-prod-local-dev-closure-2026-05-08.md`) applies unchanged.
- Local/E2E/test runs must continue to use the in-memory provider. The bypass conditions in §2 are the seam tests use to exercise real 429 behavior without paying for external quota; the adapter must not be reachable from `NODE_ENV=test` paths unless `RATE_LIMIT_ENFORCE` / `RATE_LIMIT_ENFORCE_IN_TESTS` is set **and** the test explicitly opts into the adapter. CI defaults must not call the paid provider.
- Cost-shape decisions are part of the approval, not deferred to "we'll see in production": eviction/expiry policy, max key cardinality, per-tier cost expectation under `auth`'s 15-minute window, and the runaway-cost cap (e.g., daily request budget or monthly USD cap) must be named in the approval record. If the provider has no native cap, ops must wire one in front of it.
- Failure mode is named in advance. If the adapter is unavailable (provider outage, credential rotation, exhausted quota), the documented behavior is to fail closed (return a 5xx via the existing `ApiErrorHandler` surface) rather than silently fall back to memory. A documented fail-open mode is allowed only with a separately signed exception, because it converts a durable-limiter outage into a silent regression to single-instance enforcement.
- This report does not authorize anyone to provision, sign up for, or call any paid limiter store. It also does not authorize an exception to the current memory-only path; that exception is Option A in §1 and still requires a written launch exception.

## 5. What this report does not do

- It does not select Upstash, Vercel KV/Edge Config, Cloudflare KV/Durable Objects, Postgres/Supabase, hosted Redis, Memcached, Dragonfly, or any other store.
- It does not install, import, or call any external/paid rate-limit SDK.
- It does not mutate env, secrets, dashboards, live Supabase, or repo configuration outside this single artifact.
- It does not advance the Phase 0/1 closure matrix; it makes the remaining D2 ask checklist-shaped so the approval-day PR is reviewable in one pass.
- It does not pre-stage adapter code, adapter tests, dependency adds, or guard relaxations. Each of those edits remains a post-approval action.
